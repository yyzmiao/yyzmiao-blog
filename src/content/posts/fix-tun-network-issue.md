TUN 模式（虚拟网卡模式）是 Clash 系列客户端实现全局透明代理的核心机制，但在部分 Windows 环境下，开机或系统从休眠唤醒后会出现虚拟网卡初始化异常，导致代理彻底失效。本文记录该问题的诊断过程与最终解决方案。

## 故障现象

该问题具有以下三个明确特征，可作为判断依据：

1.  **节点全红**：客户端进程正常运行，界面可打开，但延迟测试时全部节点显示超时。
2.  **关闭 TUN 即恢复**：在设置中关闭”虚拟网卡（TUN 模式）”后，网络立即恢复正常。
3.  **开启 TUN 即断连**：重新启用 TUN 模式后，网络在数秒内再次完全中断。

这一组合特征指向明确的结论：故障点不在订阅节点、服务器可用性或客户端配置，而在虚拟网卡与系统网络栈的衔接环节。

## 常规排查手段及其局限

以下方法为该问题常见的排查路径，但均无法根治：

| 排查方向 | 操作 | 结果 |
| --- | --- | --- |
| 防火墙 | 重置 Windows 防火墙规则 | 无效 |
| DNS | 切换 DNS Hijacking 开关，清理 DNS 缓存 | 无效 |
| 网卡驱动 | 在”网络连接”中手动禁用/启用虚拟网卡 | 无效 |
| 客户端 | 完全退出并以管理员身份重新运行 | 无效 |
| 系统级 | 重启电脑 | 概率性有效，不可靠 |

前四种方法均作用于驱动或应用层，未触及问题根源。重启电脑之所以偶尔有效，是因为系统重新初始化了网络栈整体状态，但这属于副作用式的修复，无法保证下次开机不再复现。

## 根本原因

TUN 虚拟网卡在系统启动或从休眠唤醒时，其初始化过程可能与系统网络栈的加载时序发生冲突，导致该适配器进入路由异常的中间状态——网卡处于”已启用”但路由表未正确写入的状态。此时通过图形界面禁用再启用，走的仍是驱动层的浅层重置，无法清除这一状态；只有对适配器执行底层重启，才能强制刷新其网络配置。

## 解决方案：通过 PowerShell 重置网络适配器

### 步骤一：关闭 TUN 模式并退出客户端

在重启网卡前，需先在客户端设置中关闭 TUN 模式并完全退出程序，避免适配器因被占用而重启失败。

### 步骤二：以管理员权限打开 PowerShell

右键点击”开始”菜单（或按 `Win + X`），选择 **Windows PowerShell（管理员）** 或 **终端（管理员）**。必须以管理员权限运行，否则命令将因权限不足而报错。

### 步骤三：执行网卡重启命令

**方案一：重启全部网络适配器**

适用于不确定虚拟网卡具体名称的情况。该命令会重启系统上所有网络适配器，执行期间网络会短暂中断数秒：

```
Get-NetAdapter | Restart-NetAdapter
```

**方案二：仅重启目标虚拟网卡**

适用于不希望影响当前使用中的物理网卡（如 Wi-Fi、以太网）的情况。先查看适配器列表：

```
Get-NetAdapter
```

从返回结果的 `Name` 列中找到对应的虚拟网卡名称（常见命名如 “Core” 或客户端自定义名称），随后执行：

```
Restart-NetAdapter -Name "你的虚拟网卡名称"
```

### 步骤四：重新启动客户端

命令执行完成后，重新启用 TUN 模式(或重启客户端) ，网络连接应恢复正常。

## 补充建议

若该问题在每次开机时稳定复现，可将 `Get-NetAdapter | Restart-NetAdapter` 封装为开机启动脚本，实现自动化修复，无需每次手动执行命令。

## 小结

当出现”关闭 TUN 模式即恢复、开启 TUN 模式即断连”这一特征性故障时，问题根源通常是虚拟网卡初始化异常，而非节点或订阅问题。相较于重装客户端或更换服务商，通过 PowerShell 执行 `Restart-NetAdapter` 强制重置适配器是更直接、更可靠的解决路径。
